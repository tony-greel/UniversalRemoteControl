## 2026-08-17 红外发送失败仍更新 App 状态（回家场景 P0）

- **现象**：用户点遥控键后 IR 发送失败（如无 IR、角度不对），Toast 提示失败，但 UI 与 SharedPreferences 中的空调状态已改变，与真机不一致；叠加实体遥控器改空调后，回家操作更易「越控越乱」。
- **根因**（事实）：`RemoteControlRepository.sendAcAction()` / `sendDiscreteCandidate()` / `sendSavedDiscretePattern()` 在调用 `transmit()` **之前**执行 `updateAcState()`，失败时不回滚；`Tcl112AcRemote.apply()` 编码过程也会改动协议层字节。
- **规则链路**：
  - 修复前：按钮 → `AcRemoteViewModel.dispatch` → `sendAcAction` → `updateAcState` + persist → `transmit`（失败时状态已脏）
  - 修复后：计算 `newState` → 编码/发射 → `commitAcStateAfterTransmit` 成功才 `updateAcState`，失败则 `tcl112AcRemote.restore(acState)`
  - B1 提示：`AcRemoteActivity` 顶部 `tvStateSyncHint` 告知 App 记录状态可能与真机不符
- **改动模块/文件**：
  - `domain/repository` — `RemoteControlRepository.kt`：新增 `commitAcStateAfterTransmit`；`sendLight`/`sendHybridLight` 改接收 `AcState`
  - `ui/ac` — `activity_ac_remote.xml`：状态同步提示 TextView `tvStateSyncHint`
  - `res/layout` — `activity_ac_remote.xml`
  - `res/values` — `strings.xml`：`ac_state_sync_hint`
  - `app/src/test/domain/repository` — `RemoteControlRepositoryTest.kt`：发射失败不持久化单测 2 项
- **方案**：最小侵入——仅在 Repository 边界调整「先发射后提交」顺序 + 失败回滚协议层；UI 加一行静态提示，不改 TCL112 编解码与配对流程
- **未动部分**：`Tcl112AcEncoder`、`Tcl112AcRemote` 编解码逻辑、`MainActivity` 配对、`AcRemoteViewModel.dispatch` 结构
- **回归建议**：
  - `./gradlew assembleDebug test`
  - 真机：遮挡 IR 后点温度/电源，确认 UI 与持久化不变；发送成功后状态正常更新
  - 进遥控页可见状态同步提示文案

## 2026-08-17 无空调时点击设置仍可进入遥控页

- **现象**：用户附近没有空调设备，点击设备列表「设置」仍直接进入 `AcRemoteActivity`。
- **根因**（事实）：`checkDeviceConnection()` 仅校验 `hasIrEmitter()`，只要手机有红外发射器即判定 Connected，未区分「附近是否有可用空调」。
- **规则链路**：
  - 修复前：`btnSettings` → `checkDeviceConnection()` → `hasIrEmitter()==true` → `AcRemoteActivity`
  - 修复后：`btnSettings` → `checkDeviceConnection()` → 需 `hasIrEmitter` + `DevicePairingStore.isPaired` → 未配对弹出连接探测对话框 → 用户确认「空调已响应」才 `markPaired` 并进入
- **改动模块/文件**：
  - `data/preference` — 新增 `DevicePairingStore.kt` / `DevicePairingPreferences.kt`
  - `domain/repository` — `RemoteControlRepository.kt`：`checkDeviceConnection` 增加配对校验；新增 `sendConnectionProbe` / `confirmDevicePairing` / `clearDevicePairing`
  - `ui/main` — `MainViewModel.kt`、`MainActivity.kt`：配对对话框（发送探测 → 用户确认是否有响应）
  - `core` — `AppContainer.kt` 注入 `DevicePairingPreferences`
  - `res/values/strings.xml` — 配对相关文案
  - `app/src/test/.../RemoteControlRepositoryTest.kt` — 未配对/已配对/探测单测
- **方案**：IR 单向通信无法自动感知空调在线，采用「发送探测 + 用户确认响应」完成配对；选「无响应/取消」则按钮显示「连接失败，需重试」，不进入遥控页
- **未动部分**：TCL112AC 编解码、`AcRemoteActivity` 遥控逻辑
- **回归建议**：
  - 无空调：点设置 → 取消或选「无响应」→ 不应进入遥控页，按钮变为重试
  - 有空调：完成配对后可正常进入；杀进程后配对状态保留

## 2026-08-17 空调模式/风速选中「自动」后无法切换

- **现象**：用户选中模式或风速「自动」后，再点其他选项无反应或高亮不切换，表现为「无法点击切换」。
- **根因**（事实 + 推测）：
  - **事实**：单选高亮 Feature 使用 `MaterialButton.isSelected` + ColorStateList 的 `state_selected` 驱动样式
  - **推测**：MaterialButton 单选交互实际走 `state_checked` / `isChecked`；`selected` 与 `checked` 状态不一致导致选中「自动」后触摸/高亮异常
  - **事实（次要）**：`AcRemoteViewModel.dispatch()` 在红外发送失败时不刷新 `acState`，Repository 已更新但 UI 仍显示旧选中项，加剧「切不过去」观感
- **规则链路**：
  - 点击：`MaterialButton` → `AcRemoteActivity.bindActions()` → `AcRemoteViewModel.sendAction()` → `RemoteControlRepository.sendAcAction()` → 更新 `AcState.mode` / `fanSpeed`
  - 回显（修复前）：`acState` LiveData → `renderState()` → `button.isSelected` → `state_selected` ColorStateList
  - 回显（修复后）：`acState` LiveData → `renderState()` → `MaterialButtonToggleGroup.check()` → `state_checked` ColorStateList
- **改动模块/文件**：
  - `ui/ac` — `AcRemoteActivity`：模式/风速改用 `MaterialButtonToggleGroup` + `addOnButtonCheckedListener`；`updateModeSelection` / `updateFanSelection` 改为 `toggleGroup.check()`
  - `ui/ac` — `AcRemoteViewModel`：发送失败时也 `_acState.value = repository.getAcState()`
  - `res/layout` — `activity_ac_remote.xml`：`toggleMode` / `toggleFan` 包裹 8 个按钮
  - `res/color` — `ac_toggle_*.xml`：补充 `state_checked` 条目
- **方案**：最小侵入——仅改 UI 选中态实现与 ViewModel 状态同步；不改红外协议、Repository 发送逻辑、RemoteAction 枚举
- **未动部分**：`Tcl112AcRemote`、`RemoteControlRepository.sendAcAction()` 分支、TCL112AC 编解码
- **回归建议**：
  - `./gradlew assembleDebug`
  - 真机：依次切换模式（含「自动」）与风速（含「自动」），确认高亮跟随且可反复切换
  - 无 IR 硬件时确认 UI 仍能切换（失败提示 + 选中态同步）

## 2026-08-17 方式三 HYBRID_ALL 混合轮询仅发送首条策略即返回

- **现象**：用户开启「方式三：自动轮询所有策略」后点关灯/开灯，App 显示发送成功，但真机上灯光仍可能无效；代码审查发现一次点击理论上应串行发送 7 种策略（1 状态位 + 6 独立候选），实际只发出第 1 条红外波形。
- **根因**（事实）：`RemoteControlRepository.sendHybridLight()` 在 `for` 循环内遇到第一次 `TransmitResult.Success` 即 `return`，后续 6 种候选码从未调用 `transmit()`。
- **规则链路**：`AcRemoteActivity`（关灯/开灯）→ `AcRemoteViewModel.sendAction()` → `RemoteControlRepository.sendLight()` → `sendHybridLight()` → `transmit()` → `AndroidIrTransmitter`；bug 位于 `sendHybridLight()` 循环提前返回。
- **改动模块/文件**：
  - `domain/repository` — `RemoteControlRepository.sendHybridLight()`：循环内累积成功/失败，全部尝试后再返回
  - `domain/repository`（测试）— 新增 `RemoteControlRepositoryTest.kt` 断言 HYBRID 发送 7 次
  - `data/preference` — 新增 `LightControlConfigStore` 接口，`LightControlPreferences` 实现之，便于 Repository 单测注入内存配置
- **方案**：最小侵入——仅改混合轮询返回逻辑，不改 TCL112AC 编解码、方式一/二分支；引入 `LightControlConfigStore` 抽象仅为测试替身，运行时仍用 `LightControlPreferences`。
- **未动部分**：`Tcl112AcRemote`、`Tcl112AcEncoder`、`TclLightPatternLibrary` 候选定义、`AcRemoteActivity` UI 逻辑未改
- **回归建议**：`./gradlew testDebugUnitTest --tests "*.RemoteControlRepositoryTest"`；真机再试方式三，观察是否比修复前更易命中有效码（真机效果未核实）

## 2026-08-17 构建失败：JDK 25 与 Gradle 8.9 / Kotlin 插件不兼容

- **现象**：执行 `./gradlew assembleDebug` 失败，报错 `java.lang.IllegalArgumentException: 25.0.2`；后续升级 Gradle 9.1 后又因 AGP 9 内置 Kotlin 导致 `kotlin-android` 插件冲突、`kotlinOptions` 无法解析；依赖下载偶发 TLS 握手失败/超时。
- **根因**（事实）：
  - 本机 JDK 为 25.0.2（Android Studio JBR），Gradle 8.9 + Kotlin 2.0.21 无法识别该 Java 版本
  - AGP 9.0+ 默认启用内置 Kotlin，不再允许单独应用 `org.jetbrains.kotlin.android`
  - `dl.google.com` / `repo.maven.apache.org` 在部分网络环境下 TLS 握手失败或下载超时
- **规则链路**：`./gradlew` → `gradle-wrapper.properties` → `settings.gradle.kts` / `build.gradle.kts` / `app/build.gradle.kts` → 依赖解析 → `compileDebugKotlin`
- **改动模块/文件**：
  - `gradle/wrapper/gradle-wrapper.properties` — Gradle 8.9 → **9.1.0**
  - `build.gradle.kts` — AGP 8.7.3 → **9.0.1**；移除 `kotlin-android` 插件声明
  - `app/build.gradle.kts` — 移除 `kotlin-android` 插件与 `kotlinOptions` 块
  - `settings.gradle.kts` — 优先使用阿里云 Maven 镜像
  - `gradle.properties` — 增加 HTTP 连接/读取超时
- **方案**：采用 AGP 9 内置 Kotlin（最小侵入，无需单独维护 KGP 版本）；仓库镜像解决依赖下载；未改动业务源码与红外协议层。
- **未动部分**：`data/protocol/tcl`、`domain/repository`、`ui/**` 等业务逻辑未改
- **回归建议**：`./gradlew assembleDebug test`；换 JDK 17/21 环境也应能构建

## 2026-08-17 单元测试 Tcl112AcRemoteTest checksum 断言错误

- **现象**：`./gradlew test` 失败，`calcChecksum_matchesDefaultState` 报 `expected:<3> but was:<-125>`（即 `0x03` vs `0x83`）。
- **根因**（事实）：测试用例对 IRremoteESP8266 `sumBytes` 按 uint8 累加的结果理解有误；默认 14 字节状态（末字节占位 0）的前 13 字节校验和应为 `0x83`，非 `0x03`。
- **规则链路**：`Tcl112AcRemoteTest` → `Tcl112AcEncoder.calcChecksum()` → `Tcl112AcRemote.refreshChecksum()`（运行时校验）
- **改动模块/文件**：
  - `app/src/test/java/com/universalremote/control/data/protocol/tcl/Tcl112AcRemoteTest.kt`
- **方案**：仅修正测试期望值，编码器实现与 IRremoteESP8266 一致，未改协议逻辑。
- **未动部分**：`Tcl112AcEncoder.kt`、`Tcl112AcRemote.kt` 未改
- **回归建议**：`./gradlew testDebugUnitTest --tests "*.Tcl112AcRemoteTest"`
